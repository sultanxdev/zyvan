# Retry Policy & Backoff Formulation

To avoid overwhelming recovering servers with synchronized retries, Zyvan implements **Exponential Backoff with Full Jitter** (based on AWS research on contention resolution).

---

## The Mathematical Model

For attempt number `i` in `{1, 2, ..., N}`:

```
BaseDelay[i]   = InitialInterval * (Multiplier ^ (i - 1))
CappedDelay[i] = min(MaxInterval, BaseDelay[i])
ActualDelay[i] = UniformRandom(0, CappedDelay[i])
```

---

## Configurable Destination Policy

```json
{
  "retry_policy": {
    "max_attempts": 6,
    "initial_interval_sec": 10,
    "backoff_multiplier": 2.0,
    "max_interval_sec": 43200
  }
}
```

<AccordionGroup>
  <Accordion title="What happens when an endpoint responds with 429 Too Many Requests?">
    If the endpoint includes a standard `Retry-After: <seconds>` HTTP header, Zyvan respects the server's requested delay instead of standard exponential calculation, provided it falls within the destination's `max_interval_sec` boundary.
  </Accordion>
  <Accordion title="Why is Jitter mandatory in high-scale systems?">
    Without jitter, if 1,000 deliveries fail simultaneously during a network hiccup, all 1,000 retries would fire at the exact same millisecond 5 seconds later, instantly crashing the destination again. Jitter spreads the 1,000 retries evenly across the delay window.
  </Accordion>
</AccordionGroup>

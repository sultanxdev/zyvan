# Idempotency and Deduplication

In distributed systems, the network is fundamentally unreliable. A client application might send an HTTP `POST` to publish an event, and the Zyvan server successfully receives and commits the event—but a transient network timeout or dropped TCP packet causes the client to believe the request timed out.

```text
Client Application ──► POST /v1/events ──► Zyvan Server (Committed to DB)
        ▲                                          │
        │                                          ▼
   HTTP Timeout ◄─────────────────── Network Drop (Response Lost)
        │
   Client Retries ──► POST /v1/events ──► DUPLICATE EVENT! (Without Idempotency)
```

Without idempotency, client retries cause **duplicate event ingestion**, triggering duplicate billing charges, double-provisioned customer accounts, or multiple conflicting webhook deliveries.

Zyvan solves this with **database-enforced atomic deduplication** powered by the `Idempotency-Key` header.

## How Idempotency Works

```mermaid
sequenceDiagram
    autonumber
    actor App as Client Application
    participant Zyvan as Zyvan Ingestion API
    participant DB as PostgreSQL (Unique Index)

    App->>Zyvan: POST /v1/events (Idempotency-Key: "tx_order_998124")
    Zyvan->>DB: INSERT INTO events (project_id, idempotency_key, ...)
    DB-->>Zyvan: Success (Row Created)
    Zyvan-->>App: 202 Accepted (event_id: "evt_01", duplicate: false)

    Note over App,Zyvan: Network connection drops; client retries the exact same request

    App->>Zyvan: POST /v1/events (Idempotency-Key: "tx_order_998124")
    Zyvan->>DB: INSERT INTO events (project_id, idempotency_key, ...)
    DB-->>Zyvan: Unique Constraint Violation (duplicate key)
    Zyvan->>DB: SELECT event by (project_id, idempotency_key)
    Zyvan-->>App: 200 OK (event_id: "evt_01", duplicate: true)
```

## Database-Level Invariants

Unlike lightweight caching layers (such as Redis) which are vulnerable to cache eviction, key expiration race conditions, or replication lag, Zyvan enforces idempotency at the database engine level:

```sql
CREATE UNIQUE INDEX idx_events_project_idempotency 
ON events (project_id, idempotency_key) 
WHERE created_at > NOW() - INTERVAL '24 hours';
```

### Key Behavioral Rules

1. **24-Hour Active Window**:
   Idempotency keys are guaranteed unique within a rolling 24-hour window per project.
2. **Deterministic Payload Matching**:
   If a client retries a request with the same `Idempotency-Key` but changes the `event_type` or `payload`, Zyvan detects the conflict and rejects the request with `409 Conflict`:
   ```json
   {
     "error": {
       "code": "IDEMPOTENCY_KEY_MISMATCH",
       "message": "An event with this idempotency key was previously submitted with a different payload."
     }
   }
   ```
3. **Concurrent Execution Safety**:
   If two identical requests with the same key arrive at the exact same millisecond, PostgreSQL row-level locking ensures that exactly one transaction succeeds in creating the row, while the second transaction waits and safely receives the existing event.

## Best Practices for Choosing Idempotency Keys

<Steps>
  <Step number={1} title="Use Business Domain Identifiers">
    Derive keys directly from the primary entity in your database:
    - Orders: `order_ord_998124_created`
    - Subscriptions: `sub_883109_renewal_2026_03`
    - Invoices: `inv_554109_paid`
  </Step>

  <Step number={2} title="Never Use Random UUIDs on Retries">
    If your HTTP client generates a random `v4()` UUID inside the retry loop, every retry will present a different key, entirely defeating deduplication. Generate the UUID once before initiating the operation.
  </Step>

  <Step number={3} title="Combine Action + Entity ID">
    If an entity experiences multiple events throughout its lifecycle (e.g. `order.created`, `order.shipped`), qualify the key with the action name:
    ```typescript
    const idempotencyKey = `order_${order.id}_shipped`;
    ```
  </Step>
</Steps>

## SDK Integration & Safe Automatic Retries

The official `@zyvan/sdk` integrates idempotency directly into its retry engine:

```typescript
import { ZyvanClient } from '@zyvan/sdk';

const zyvan = new ZyvanClient({
  apiKey: process.env.ZYVAN_API_KEY!,
  projectId: 'prj_live_01H8X92M4Q',
});

// The SDK automatically attaches this key to the HTTP header
const event = await zyvan.events.create({
  eventType: 'payment.completed',
  tenantId: 'cust_enterprise_01',
  idempotencyKey: `tx_stripe_charge_${charge.id}`,
  payload: {
    chargeId: charge.id,
    amount: charge.amount,
    currency: charge.currency,
  },
});

if (event.duplicate) {
  console.log(`Event was already processed previously: ${event.id}`);
} else {
  console.log(`New event published: ${event.id}`);
}
```

<Callout type="note" title="SDK Operation Safety">
  In `@zyvan/sdk`, transient network failures (connection drops, socket timeouts) on `POST` requests are **only retried if an idempotency key was provided**. Unkeyed mutations are intentionally never retried over the network to protect you from duplicate execution.
</Callout>

Zyvan MVP v0.1
This should be your actual implementation baseline now. The PRD is broader than what you should build immediately, so MVP v0.1 deliberately freezes the scope around the reliability core rather than trying to implement the entire product vision. The PRD itself says the first release should focus on durable ingestion, at-least-once delivery, idempotency, retries, dead-letter recovery, replay, debugging, tenant isolation, and fast onboarding.

Product
Zyvan — Reliable Webhook & Event Delivery Infrastructure

This is the heart of Zyvan.

Request

Ingestion processing

  ↓

  ↓

The API must not wait for the destination HTTP request to finish before responding. Durable acceptance comes first.

7. Idempotency
This is one of the features you should absolutely demonstrate in interviews.
Rule
Same project + same idempotency_key
             ↓
       Same logical event
Two concurrent requests using the same idempotency key must not create two logical events.
Example:
Request 1 → idempotency_key = order_123
Request 2 → idempotency_key = order_123

Result:
Request 1 → evt_001
Request 2 → evt_001
Not:
evt_001
evt_002

11. Attempt tracking
Every actual HTTP delivery should create an Attempt.
Attempt
id
delivery_id
attempt_no
started_at
ended_at
response
status_code
latency_ms
outcome
error_message
Example:
Delivery D1

Attempt 1 → 500 → 210ms → failed
Attempt 2 → timeout → 5000ms → failed
Attempt 3 → 200 → 180ms → success
The attempt history must remain immutable because it is what lets an engineer reconstruct the incident.

12. Retry engine
Retry on
HTTP 5xx
Connection failure
Timeout
Other configured transient failures
Don't blindly retry
Permanent 4xx errors
Invalid requests
Authorization failures
Policy-defined terminal errors
Retry strategy
Attempt 1
   ↓
wait
   ↓
Attempt 2
   ↓
exponential backoff + jitter
   ↓
Attempt 3
   ↓
...
   ↓
retry exhausted
   ↓
DLQ
The SRS explicitly requires exponential backoff + jitter and classification between retryable and terminal errors.
A simple MVP policy could be:
max_attempts = 5
base_delay = 1s
max_delay = configurable
jitter = enabled
That exact numeric policy is your implementation choice, not a value specified by the PRD.

13. Dead Letter Queue
When retry attempts are exhausted:
Delivery
   ↓
Retry exhausted
   ↓
Dead Letter
Store:
event_id
reason
created_at
But do not throw away attempt history.
The PRD requires exhausted/expired events to enter a recoverable terminal state with complete history.

14. Replay
Replay must not mutate the original attempt history.
Example:
Original:

Attempt 1 → 500
Attempt 2 → 500
Attempt 3 → DLQ


Replay:

Replay R1
   ↓
New Delivery/Attempt
   ↓
Attempt 4 → 200
The PRD explicitly requires replay to create a new attempt lineage rather than overwrite historical attempts.
Endpoint
POST /v1/events/{event_id}/replay
Response:
{
  "replay_id": "replay_01J...",
  "status": "queued"
}

15. HMAC webhook signing
Outbound requests should include a versioned signature.
Example conceptual headers:
X-Zyvan-Signature: v1=<signature>
X-Zyvan-Timestamp: <timestamp>
X-Zyvan-Delivery-Id: <delivery_id>
X-Zyvan-Event-Id: <event_id>
Sign:
timestamp + raw payload
using:
HMAC-SHA256
The PRD specifies HMAC-SHA256, versioned signatures, timestamp information and delivery/event IDs.

Zyvan Backend PRD v0.1
This is the backend implementation PRD for the Zyvan MVP, derived from the backend architecture, SRS, API requirements, reliability model, security requirements, and technology standards in your main PRD.
The backend's job is simple to state but difficult to implement correctly:
Accept an event durably, process it asynchronously, deliver it reliably, recover from failures, preserve the complete history, and expose enough state for the dashboard to explain exactly what happened.
The original PRD explicitly defines PostgreSQL as the authoritative source of event/delivery state and Redis/BullMQ as the execution layer.

35. Transaction boundaries
The most important transaction:
BEGIN

insert event
create delivery
commit

THEN

enqueue job
But this creates a subtle failure problem:
DB commit succeeds
queue publish fails
The event must not be lost.
Therefore v0.1 should include a recovery/reconciliation mechanism.
For example:
PostgreSQL
   ↓
event/delivery = queued
   ↓
queue publish
and a periodic recovery process:
Find queued deliveries
without active queue jobs
        ↓
re-enqueue
This follows the PRD requirement that accepted asynchronous work remain recoverable after process failure.
Do not claim a full transactional outbox implementation unless you actually build one. A DB-backed reconciliation mechanism is enough for your first implementation.
